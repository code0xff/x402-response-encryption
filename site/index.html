Paid responses only the payer can read.

An x402 response passes through CDNs, reverse proxies, payment gateways and marketplaces that terminate TLS and can log or cache it. With this extension the seller encrypts the body to a key the client committed inside its payment signature, so everything in between relays ciphertext.

One paid call, end to end

The payment signature carries the client's key

The client generates a fresh key pair for each request and puts a commitment to its public key in a field the payment already signs. An intermediary that swaps the key breaks the signature. One that swaps the seller's key has to redirect the payment on-chain.

client                     intermediary (CDN, gateway)           seller
  │ request ──────────────────────────────────────────────────────▶
  │ ◀──────────────────────────────── 402  key M, attested by payTo
  │ verify attestation, generate (e, E)
  │ c = keccak256(tag ‖ E ‖ keyId ‖ requestHash ‖ r)
  │ sign payment with nonce = c

  │                                       K = HKDF(ECDH(m, E), digest)
  │ ◀──────────────────────────── 200  AES-256-GCM envelope
  │ K = HKDF(ECDH(e, M), digest), decrypt

How it works

Four steps on top of the existing exact scheme

No new payment scheme and no change to the facilitator. The extension adds fields to the 402 and the payment payload, and replaces the response body with an envelope.

01

Attest

The seller signs its encryption key once with the payTo key (EIP-712, EIP-1271 for contracts). This can be done offline.

02

Commit

The client checks the attestation against the payTo it pays, then commits a per-request ephemeral key and the request hash into the signed nonce.

03

Check

Before settlement the seller recomputes the commitment from the request it received. A changed key, body, path or URL is rejected, and nothing settles.

04

Encrypt

The seller encrypts the response to that key. The client decrypts it. Lost responses are resent byte for byte from storage, without a second charge.

Payment schemes

The binding does not depend on EIP-3009

The commitment goes in whichever client-chosen field the payment signature covers. Each profile fixes where it sits, which digest salts the key derivation, and how the seller checks the signature locally.

Quick start

Seller middleware and a client fetch wrapper

The reference packages wrap the official @x402/express middleware and run in this repository's workspace. They are not published to npm.

1 · run the tests and the testnet demo
git clone https://github.com/code0xff/x402-response-encryption
cd x402-response-encryption && npm install
npm test
npm run demo           # EIP-3009 on Base Sepolia, needs a funded .env
npm run demo:permit2   # Permit2
2 · seller (Express)
import { createResponseEncryption } from '@x402-response-encryption/express';

const enc = createResponseEncryption({ keys: [{ privateKey, attestation }] });
resourceServer.registerExtension(enc.extension);

app.use(enc.before);                     // binding check before settlement
app.use(paymentMiddleware({
  'POST /v1/report': { accepts, extensions: enc.declaration },
}, resourceServer));
app.use(enc.after);                      // encrypts the paid response
app.post('/v1/report', (req, res) => res.json(report));
3 · client
import { wrapFetchWithEncryptedPayment } from '@x402-response-encryption/fetch';

const pay = wrapFetchWithEncryptedPayment(fetch, { signer, pinnedPayTo });
const res = await pay('https://api.seller.example/v1/report', { method: 'POST', body });
console.log(await res.json());           // decrypted; plaintext from the network is refused

Scope

What it protects, and what it does not

Protected

  • Response bodies from every party between seller and client, including the payment gateway in a gateway deployment.
  • Key substitution: swapping the client's key breaks the payment signature and the seller refuses before settlement.
  • Replay to another request: the commitment covers method, URL and body.
  • Lost responses: the same payload gets the stored envelope, with no second settlement.

Not covered

  • Request bodies, headers and the URL. They stay visible to anything that terminates TLS.
  • Metadata: who paid whom, how much, when, and the response size.
  • A seller that leaks its own data, or a client that shares it.
  • A substituted payTo in the core profile: the client must know payTo out of band, or use the optional did:web profile.

FAQ

Questions

Isn't TLS enough?

TLS ends at the first party that terminates it. A CDN, a reverse proxy or a payment gateway in front of the seller reads and can log or cache the response. For an agent buying financial or personal data, that party may not be the one it paid.

Does the facilitator need to change?

No. The commitment is an ordinary nonce or memo to the facilitator. The seller checks it before asking the facilitator to settle.

Does the client's wallet need new features?

No. The ephemeral key is generated by the client library, not the wallet. The wallet signs the same EIP-3009, Permit2 or Solana payment it signs today.

What happens if the encrypted response is lost?

The client resends the identical paid request. The seller returns the envelope it stored after settlement, byte for byte, and does not settle or run the request again.

Is this part of x402?

Not yet. It is a design draft submitted for discussion in x402-foundation/x402#4223. Comments and reviews are welcome there.
